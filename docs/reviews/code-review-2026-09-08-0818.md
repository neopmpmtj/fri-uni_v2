## Findings

### Medium

**M1. Stale `powers.default_indoor` after item power change (Add default quotes wrong capacity)**

| | |
| --- | --- |
| **Location** | [`proformas/services.py`](../../proformas/services.py) `add_default_split` (986–1005); gap in `save_item` (832–853) |
| **Introduced** | PR #1 (`f44ee4e`) — relies on `power.default_indoor` FK without runtime power match |
| **What happens** | Staff can change an indoor item’s `power` via the Items drawer (`ItemForm` includes `power`). `save_item` does **not** clear or revalidate `Power.default_indoor` pointers on other power rows. `validate_power_default_indoor` runs only when saving a **Power** row, not when saving the **Item**. If power 9k BTU still lists the item as `default_indoor` but the item’s `power_id` was moved to 12k BTU, Add default for a room in the 9k band **succeeds** and inserts the 12k indoor — no validation error, wrong quote. |
| **Staff trigger** | Edit item power on Items page, then Add default on a draft for a volume in the old band |
| **Bugbot** | Same finding ([Bugbot](4efd82fe-7ed4-4c9b-b133-809872dfc219)) |
| **Suggested fix** | (a) In `add_default_split`, after resolving `indoor = power.default_indoor`, call the same check as `validate_power_default_indoor` (reject if `indoor.power_id != power.pk`); and/or (b) in `save_item`, when `power` changes on an indoor item, `Power.objects.filter(default_indoor=item).update(default_indoor=None)` or block the edit if the item is a volume default. Add a unit test that changes item power and asserts Add default raises or re-picks correctly. |

**Remediation (2026-09-08):** Fixed in [`proformas/services.py`](../../proformas/services.py): `save_item` clears `Power.default_indoor` when an indoor item’s `power` changes; `add_default_split` calls `validate_power_default_indoor(power)` before insert. Tests: `test_save_item_clears_stale_default_indoor_when_power_changes`, `test_add_default_split_rejects_stale_default_indoor` in [`test_add_default.py`](../../proformas/tests/test_add_default.py).

## Scalability — proforma line creation beyond AC splits

Assessment for expanding into heating (furnaces, heat pumps, etc.).

### What is already extensible

- **`families`** — product class is modeled; docs and seed assume “Air conditioners” first, with underfloor/DHW noted as later families (`data-points.md`).
- **`powers`** — `unit` is free text; docs mention kW for non-AC ratings later.
- **Catalog CRUD** — families, design lines, items, matches, and manual **Add split** / **Add multi** drawers are generic enough to catalogue new SKUs once pairing rules are known.
- **Issued snapshot model** — product-agnostic; new equipment types do not require schema changes for freeze-at-issue.

### What is AC / split-centric today

| Layer | Constraint |
| ----- | ---------- |
| **`Item.kind`** | Only `indoor` \| `outdoor`. No standalone “unit” or “accessory” kind. |
| **Issue validation** | Every indoor line must have an outdoor parent; split outdoors must have exactly one indoor (`_validate_systems_for_issue`). |
| **Add default** | AC workflow only: room m³ → BTU band on `powers` → default indoor → auto 1-port split outdoor. |
| **Pairing** | `item_matches` + `parent_line` assume outdoor/indoor HVAC splits. |
| **Tubing** | Refrigerant line metaphor; may not apply to ducted heat or furnaces. |
| **UI copy / i18n** | “Room volume”, “Add default”, design-line navigation tuned for wall AC. |

### Product-type fit

| Product | Fit with current model | Effort |
| ------- | ---------------------- | ------ |
| **Split heat pump** (outdoor + indoor) | Good — same shape as AC; new family + matches + kW/`powers` bands | **Low–medium** — mostly catalog and sizing rules, not core schema |
| **Multi-split heat pump** | Good — existing multi outdoor flow | **Low** once catalogued |
| **Standalone furnace / boiler / water heater** | Poor — no outdoor parent; issue rules would reject a single line | **Medium–high** — new line type or `kind`, relax issue validation, new “Add …” action |
| **Hybrid quotes** (AC + furnace) | Possible manually if both fit pairing rules; Add default stays AC-only | **Medium** — family-aware entry flows |

### Conclusion

The codebase is **well prepared for more HVAC equipment that follows the outdoor/indoor split or multi-split pattern** (including many heat pumps). It is **not yet prepared for standalone heating products** or family-specific “one-click” defaults without further design:

1. Decide how standalone units appear on quotes (new `kind`, nullable `parent_line` with relaxed issue rules, or accessory lines).
2. Add **family- or product-type-specific** quick-add actions (Add default is not a generic template).
3. Separate **sizing** from AC m³→BTU (furnace kW, heat loss, etc.) — `powers` can hold numbers but semantics differ.
4. Revisit **tubing / labour** line attributes per product class.

Heating expansion deferred to [`project-plan.md`](../project-plan.md) backlog (2026-09-08). Preliminary plan update records furnace + radiator circuit shape.
